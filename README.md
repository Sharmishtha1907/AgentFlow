# AgentFlow

**A distributed multi-agent AI execution platform**

AgentFlow is a backend platform designed to accept natural-language requests, break them into smaller tasks, execute those tasks through distributed workers, and aggregate their results into a final response.

The system uses PostgreSQL as its source of truth and Apache Kafka for asynchronous communication between components.

## 1. Architecture Overview

AgentFlow follows a modular architecture with independently runnable components.

### High-level workflow

1. A user submits a request through the FastAPI application.
2. An execution record is created in PostgreSQL.
3. A planner agent converts the request into a collection of tasks.
4. Task dependencies form a Directed Acyclic Graph (DAG).
5. The scheduler identifies tasks whose dependencies are satisfied.
6. Ready tasks are dispatched through the transactional outbox and Kafka.
7. Workers consume tasks and execute them.
8. Task attempts and results are persisted in PostgreSQL.
9. The execution coordinator aggregates completed task results.
10. The final execution result is stored and returned to the user.

### Architecture components

| Component | Responsibility |
|---|---|
| FastAPI | REST API and request handling |
| PostgreSQL | Durable application state |
| SQLAlchemy | ORM and database operations |
| Outbox Publisher | Reliable event publishing |
| Apache Kafka | Asynchronous event transport |
| Scheduler | Task readiness and dispatch |
| Planner Agent | Natural-language request decomposition |
| Worker | Task execution |
| Result Processor | Result persistence and aggregation |

## 3. Database Design

PostgreSQL is the source of truth for execution state.

The application currently uses seven core tables.

| Table | Purpose |
|---|---|
| `users` | Stores user information |
| `executions` | Stores top-level user requests and execution lifecycle |
| `tasks` | Stores individual units of work |
| `task_dependencies` | Stores dependencies between tasks |
| `task_attempts` | Tracks individual task execution attempts |
| `task_results` | Stores output generated by task attempts |
| `outbox_events` | Stores events awaiting publication to Kafka |

### Important database design decisions

- UUID primary keys for distributed identifier generation.
- PostgreSQL JSONB for flexible task payloads and results.
- UTC timestamps for consistent event ordering.
- Foreign keys and database constraints for referential integrity.
- Indexes on frequently queried columns.
- Unique constraints to prevent duplicate task attempts and results.
- Transactional outbox pattern to avoid database/Kafka dual-write inconsistencies.

## 4. Kafka Design

Kafka is used for asynchronous communication between the scheduler, publisher, and workers.

### Topics

| Topic | Purpose |
|---|---|
| `agentflow.tasks` | Dispatches tasks to workers |
| `agentflow.task-results` | Transports task completion events |
| `agentflow.tasks.dlq` | Stores events that cannot be processed successfully |

### Kafka configuration

The local development environment uses a single-node Kafka broker in KRaft mode.

- Host application bootstrap server: `localhost:9092`
- Docker-network bootstrap server: `kafka:29092`
- Replication factor: `1`
- Default partition count: `3`

Task IDs should be used as Kafka message keys where per-task ordering is important.

The system assumes at-least-once message delivery. Consumers must therefore be idempotent.

## 5. Transactional Outbox Pattern

The transactional outbox pattern ensures that database changes and event creation happen in the same PostgreSQL transaction.

Instead of publishing directly to Kafka from an API request:

1. The application updates its database state.
2. It inserts an event into `outbox_events` in the same transaction.
3. The transaction commits.
4. The Outbox Publisher claims unpublished events.
5. The publisher sends events to Kafka.
6. After Kafka acknowledges delivery, the event is marked as published.

The outbox uses leases and row locking (`FOR UPDATE SKIP LOCKED`) to support multiple publisher processes without simultaneously claiming the same event.

Duplicate delivery remains possible, so downstream consumers must be idempotent.

## 7. Local Development Setup

### Prerequisites

- Python 3.11+
- Docker Desktop
- Git

### Step 1: Clone the repository

```bash
git clone <repository-url>
cd AgentMe
```

### Step 2: Create a virtual environment

Windows PowerShell:

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
```

### Step 3: Install dependencies

```bash
pip install -r requirements.txt
```

If dependencies are not yet fully listed in `requirements.txt`, install the required packages individually during development.

### Step 4: Configure environment variables

Create a `.env` file in the project root.

Example:

```env
DB_USER=web
DB_PASSWORD=web
DB_HOST=localhost
DB_PORT=5432
DB_NAME=agentme

KAFKA_BOOTSTRAP_SERVERS=localhost:9092
```

Do not commit `.env` or real credentials to version control.

### Step 5: Start infrastructure

```bash
cd deployment/local
docker compose up -d
```

Check running containers:

```bash
docker compose ps
```

### Step 6: Create database tables

Run the project's table creation script from the appropriate Python environment and project root.

```bash
python -m backend.database.create_table
```

The current development setup uses SQLAlchemy `Base.metadata.create_all()` rather than Alembic migrations. Note that `create_all()` creates missing tables but does not modify existing table schemas.

### Step 7: Create Kafka topics

```bash
python -m backend.kafka.topic_manager
```

### Step 8: Start the FastAPI application

```bash
uvicorn backend.main:app --reload
```

API documentation:

```text
http://localhost:8000/docs
```

Health check:

```text
http://localhost:8000/health
```

## 8. API Overview

Current API functionality includes CRUD and read operations for the core execution entities.

### Executions

| Method | Endpoint | Purpose |
|---|---|---|
| POST | `/api/v1/executions` | Create execution |
| GET | `/api/v1/executions` | List executions |
| GET | `/api/v1/executions/{execution_id}` | Get execution |
| GET | `/api/v1/executions/user/{user_id}` | Get user's executions |
| PATCH | `/api/v1/executions/{execution_id}/status` | Update execution status |
| PATCH | `/api/v1/executions/{execution_id}/result` | Update final result |
| DELETE | `/api/v1/executions/{execution_id}` | Delete execution |

### Tasks

| Method | Endpoint | Purpose |
|---|---|---|
| POST | `/api/v1/tasks` | Create task |
| GET | `/api/v1/tasks` | List tasks |
| GET | `/api/v1/tasks/{task_id}` | Get task |
| GET | `/api/v1/tasks/execution/{execution_id}` | Get execution tasks |
| PATCH | `/api/v1/tasks/{task_id}/status` | Update task status |
| PATCH | `/api/v1/tasks/{task_id}/result` | Update task result reference |

| Method | Endpoint | Purpose |
|---|---|---|
| POST | `/api/v1/task-dependencies` | Create dependency |
| GET | `/api/v1/task-dependencies/{dependency_id}` | Get dependency |

Read-only monitoring endpoints:

- `GET /api/v1/task-attempts/{attempt_id}`

Attempts are created and updated internally by execution services.

Read-only endpoints:

- `GET /api/v1/task-results`

- `GET /api/v1/task-results/task/{task_id}`
- `GET /api/v1/task-results/task/{task_id}/attempt/{attempt_number}`

Task results are created internally by workers or execution services.

## 9. Reliability and Consistency

Important design principles:

- PostgreSQL is the source of truth.
- Kafka is used for transport, not durable application state.
- The outbox pattern protects event creation against dual-write failures.
- Publisher leases prevent multiple publishers from claiming the same event concurrently.
- Task attempts preserve execution history across retries.
- Task results are associated with their corresponding attempts.
- Consumers must handle duplicate messages safely.
- Task dependency validation must prevent cycles.
- Failed tasks should be retried according to their retry policy.
- Permanently failing events should eventually be routed to a dead-letter topic.
